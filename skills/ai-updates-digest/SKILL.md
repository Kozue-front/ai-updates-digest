# Claude アップデートまとめ

Claude / Anthropic の更新情報を集め、1件ずつ裏を取って「確度つきのファクト」として1枚のアーティファクトにまとめる。

このskillの価値は「漏れなさ」と「正しさ」の両立にある。Grokは X の第一報に強いが、裏取りはしない。ここでは公式の情報源を順に回り、各項目に「どこで確認したか」を付けて出す。読む人がそのまま社内外に話せる精度を目標にする。

## 2つの使い方

定型文で呼ぶのがいちばん手早い。

| モード | 定型文 | 定型文以外の入口 | 出力 |
|---|---|---|---|
| **収集モード** | `Claudeアプデ` | 「今週のClaudeアプデまとめて」など | 期間内の更新を集めたレポート |
| **検証モード** | `Claudeアプデ検証` + まとめを貼る | 他のAIやXのまとめが貼られ「合ってる?」など | 貼られた主張を1つずつ判定したレポート(+貼られたまとめに無かった重要更新) |

定型文のうしろの期間の読み方:

| 書き方 | 期間 |
|---|---|
| (なし) | 今日を含む直近7日 |
| `30日` / `14日` など | 今日を含む直近N日 |
| `10月` / `2026-09` | その月の1日〜末日(今月なら今日まで) |
| `10/1〜10/10` | その範囲 |

期間の指定が無ければ **今日を含む直近7日** とする。定型文だけで呼ばれたら、確認の質問はせずにすぐ始める(定型文にした目的が「面倒が無いこと」なので)。期間はレポート冒頭に必ず日付で書く(「今週」ではなく「2026-10-04〜2026-10-10」)。

## 手順

### 1. 期間を決め、情報源を回る

`references/sources.md` を読み、そこにある情報源を **すべて** 回る。どれか1つで「無い」と判断しない。過去に起きた失敗のほとんどは、1つの情報源しか見なかったことが原因だった。例えば 2026-10-08 の Dashboards / Motion の発表は claude.com/resources/articles にしか載らず、Release notes だけを見た調査はすべて見落とした。

公式を回り終えたら、**見落としチェック** をする。期間と「Claude」「Anthropic」「新機能」「ベータ」などを組み合わせて報道(日本語・英語)と X を検索し、まだ一覧に無い機能名が出てきたら公式ページを探して裏を取る。X は Grok が強い領域なので、ここで差を埋める。

回りながら、情報源ごとに次を控えておく。最後にレポートの「探した場所」欄になる。

- 開けたか / 開けなかったか
- 長いページなら、期間の始まりまで読み切れたか(読めた範囲)
- 見つかった件数

**Claude Code** は `scripts/claude_code_releases.py` を実行すると、npm の公開日時(公式の公開記録)とCHANGELOGを突き合わせて期間内のバージョンだけを出してくれる。コード実行が使えない・ネットワークで弾かれた場合は、`references/sources.md` の手動手順に従う。

### 2. 候補を1件ずつ裏取りする

集めた候補を「1つの変更 = 1件」に分け、それぞれ確度を付ける。

| 確度 | 条件 |
|---|---|
| ✅ 公式確認 | 公式ページを実際に開いて、その内容が書いてあった |
| 🟡 報道で一致 | 公式ページは見つからないが、独立した報道2本以上が一致 |
| ⚠️ 未確認 | ソースが1本だけ / 食い違いがある / ページを開けなかった |

判定で守ること(理由つき):

- **✅ は本文を読んだものだけ。** 一覧ページでタイトルと日付を見ただけの項目は、記事を開いて中身を確かめるまで ✅ にしない。タイトルだけでは「何が変わり、誰に関係するか」を書けないため。
- **数字は開いたページで確かめたものだけ ✅ にする。** 価格・%・クレジット額・上限などは、検索結果のスニペットや要約が古い・丸めている・別プランと混ざっていることが多い。開いたページに書いてあった数字だけを載せ、確かめられなければ数字を書かずに ⚠️ にする。
- **「見つからない」を「無い」と書かない。** 書くなら「◯◯と◯◯を探したが見つからなかった」と探した場所を添える。公式の発表は複数の場所に分散しており、見落としのほうが起きやすい。
- **同じ機能は新しい日付でもう一度探す。** 「9月にベータ・Pro/Maxから」と見つけても、その後に一般提供・全プラン展開に変わっていることがある。各項目について「その後の更新」を Release notes とブログで探し、レポートには **今の状態** を書き、経緯は1行で添える。
- **X は入口、出典は公式ページ。** 投稿の多くは公式サイトの発表を中の人が紹介しているもので、元の公式ページを見つけたらそちらを出典にする。公式アカウント(@claudeai / @AnthropicAI)の投稿は、本文を実際に読めた場合に ✅ の根拠にしてよい。社員の個人アカウント(@trq212 など)だけが根拠のものは公式発表ではないので、他の独立ソースと一致すれば 🟡、そうでなければ ⚠️ にする。
- **Releasebot など非公式トラッカーの日付は「最初に観測された日」。** 公式の日付ではないので、日付の出典としては使わず、見落とし防止(候補探し)にだけ使う。

### 3. 検証モードの追加手順

貼られたまとめを主張単位に分解し、各主張に判定を付ける。

| 判定 | 意味 |
|---|---|
| ✅ 正しい | 公式で確認できた |
| ✏️ 一部違う | 大筋は合っているが、日付・対象プラン・数字・名称などが違う。正しい内容を併記する |
| ❌ 誤り | 公式情報と矛盾する、または存在しない機能・モデル名 |
| ⚠️ 未確認 | 確かめられなかった。探した場所を書く |

そのうえで、通常の収集も同じ期間で行い、**貼られたまとめに載っていなかった重要な更新** を別セクションで出す。「元のまとめが何を落としていたか」は、検証を頼んだ人にとって価値が高い。

### 4. 使っている環境への影響を判定する

更新の一覧だけでは「で、自分は何をすればいいか」が分からない。使っている人の環境と突き合わせて、影響のあるものを拾う。詳しい判定基準と例は `references/impact.md` を読む。

1. **棚卸し**: 今の会話で見えている skill の一覧(名前と説明)、つながっているコネクタやプラグインを書き出す。会話の中でユーザーが話した自作の仕組み(Claude Code の hooks、自動化、使っているモデル名など)も含める。見えないものは推測で足さない。
2. **突き合わせ**: 期間の更新と棚卸しを1つずつ照らし、関係があるものだけに判定を付ける。

| 判定 | 意味 |
|---|---|
| 🔁 置き換え候補 | 公式の新機能が、その skill の中心の仕事を代わりにできる |
| ➕ 組み合わせ | skill はそのまま。新機能と組み合わせると良くなる |
| 🛠️ 要対応 | 更新のせいで今の使い方が壊れる・期限がある(モデル提供終了、サイト終了、パラメータのエラーなど) |

3. **判断を書く**: 🔁 には「置き換える / 併用する / 今は様子見」のどれかを、理由と「skill にしか無いもの(社内ルール、テンプレート、手順)」を添えて書く。置き換えは提案までにして、skill の削除や書き換えはしない。組織で共有している skill は持ち主が決めることなので、「持ち主に相談」と添える。
4. 関係がない skill は1件ずつ書かず、「影響なし ◯件」とまとめる。

この判定は、作った人の環境に基づく。レポートを他の人に共有するときに誤解が無いよう、レポート上にも「誰の環境で判定したか」を書く(`impact.basis`)。

### 5. アーティファクトを作る

データを `data.json` にまとめ(形は `references/data-format.md`)、`python scripts/build_report.py data.json report.html` で1枚のHTMLにする。テンプレート(`assets/report_template.html`)は、ぱっと見で分かることを優先した掲示板風のデザイン:上部に種類別の件数(NEW / UP / CHANGE / END / FIX)と信頼度ゲージ、「今週の注目」3件、「カテゴリ別」、日ごとの印が並ぶ「カレンダー」、「あなたの環境への影響」、全件を★(読む優先度)つきで並べた「更新一覧」。★は自動で付く(注目=★3、環境に影響あり・仕様変更・終了=★2、その他=★1)。アイコンは各項目の `category`(色と絵柄)と `kind`(形)から自動で決まるので、**全項目に `kind` を必ず付け、要点には `item_id` を付ける**。外部ライブラリ無しで、カテゴリと確度で絞り込める。スクリプトが「注意:」を出したら、データを直してから作り直す。デザインを毎回作り直さないこと。誰が作っても同じ見た目になるのが、このテンプレートを使う理由。

出し方は環境で変える:

- **Cowork(Artifactツールがある)**: Artifact ツールで公開する。タイトルは「Claudeアプデ 2026-10-04〜10-10」のように期間を入れる。
- **Claude.ai チャット**: HTMLアーティファクトとして会話に出す。
- どちらも使えない場合は HTML ファイルを作って渡す。

アーティファクトに載せる内容:

1. 期間、作成日、件数のサマリー(確度別・カテゴリ別)
2. **要点3つ**: 読む人の仕事の目線で「これは知っておくべき」ものを3つ選び、1〜2文で理由を書く。読む人の仕事は、会話・メモリ・使っている skill やコネクタから分かる範囲で判断する(例: マーケ支援の会社ならGA4・MA・データ基盤まわり)。分からなければ、Claude を仕事で使うチーム全般の目線で選ぶ
3. **あなたの環境への影響**: 手順4の判定
4. 更新一覧: 日付(新しい順)、カテゴリ、タイトル、何が変わったか(日本語で2〜3文)、対象(プラン・環境)、確度、出典リンク
5. 状態が変わったもの: 以前の発表から変化があった項目(ベータ→一般提供 など)
6. 検証モードのみ: 判定一覧と、元のまとめに無かった更新
7. 探した場所と読めた範囲

カテゴリは次の5つに固定する: `モデル` / `Claudeアプリ`(チャット・Cowork・モバイル・Chrome拡張・連携など) / `Claude Code` / `API・Platform`(API・SDK・Managed Agents・料金・モデル提供終了) / `会社・その他`(提携・方針・研究)。

文章は日本語。製品名・機能名・コマンド名は英語表記のまま(`/mods`、`Claude Haiku 5.5` など)。誇張(「革命的」「ついに」など)は使わず、何が変わり誰が使えるのかを書く。

### 6. チャットでの返事

アーティファクトを出したら、チャットには3〜6行で:要点3つの見出し、環境への影響(🔁 と 🛠️ があればその skill 名と判断)、⚠️未確認が何件あるか。全件をチャットに繰り返さない。
