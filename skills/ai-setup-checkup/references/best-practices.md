# 診断の基準(公式のベストプラクティス)

確認日:2026-10-13。各項目の末尾の [n] は、下の「出典」の番号。

この基準は公式ドキュメントの要点を短くまとめたもの。確認日から3か月以上たっていたら、診断の前に出典を開いて変わっていないか確かめ、変わっていた点はレポートの「基準の更新」欄に書く。

## 1. 全体の原則

- **文脈(コンテキスト)は一番大事な資源。** 埋まるほど性能が落ち、前の指示を忘れやすくなる。常に読み込まれるものほど、短く保つ価値が高い [1]
- **Claude が知らないことだけを書く。** 「この1行を消したら Claude は間違えるか?」と問い、間違えないなら消す [1][3]
- **理由を添える。** 「◯◯しない」だけより、「△△だから◯◯しない」の方が、Claude が似た場面にも応用できる [4]
- **してほしいことを書く。** 「◯◯しないで」より「◯◯して」の方が守られやすい [4]
- **強調は1か所だけ。** 「重要」「必ず」を多くの行に付けると、どれも目立たなくなる。最近のモデルは指示によく反応するので、強い言い方は使いすぎになりやすい [1][4]
- **矛盾を置かない。** 2つの指示が食い違うと、Claude はどちらかを適当に選ぶ。複数の指示ファイルは定期的に見直す [2]

## 2. 置き場所の選び方

| 中身 | 置き場所 | 理由 |
|---|---|---|
| どの会話でも当てはまる「自分について」(役割、よく使う言葉、出力の好み) | Instructions for Claude(設定の個人の指示) | 全部の会話に効く [7][8] |
| 1つの仕事の流れ(顧客、定例の成果物)の背景・型・資料 | プロジェクト(指示+資料/フォルダ) | その仕事の会話にだけ効く [7][9] |
| ときどき必要な手順・参照資料、繰り返す作業 | skill | 必要なときだけ読み込まれる [3][6] |
| Claude Code で毎回必要な、コマンド・規約・構成 | CLAUDE.md | 毎回読み込まれる [1][2] |
| 毎回、例外なく実行すべき処理 | hook(Claude Code) | 指示は「お願い」、hook は「強制」 [1][6] |
| 外のデータを読む・外で操作する | コネクタ(MCP) | ブラウザからコピペしている作業が候補 [6] |
| 他の人や別の環境でも同じ設定を使う | プラグイン | まとめて配れる [6] |

足す順番の目安 [6]:

- 同じ規約やコマンドを **2回** 間違えられた → 常に読み込まれる指示に足す
- 同じ手順を貼るのが **3回目** → skill にする
- ブラウザのタブから何度もコピーしている → コネクタにつなぐ
- 毎回必ず、頼まずに起きてほしい → hook にする
- 別のリポジトリでも同じ設定が要る → プラグインにする

## 3. 常に読み込まれる指示

対象:Claude Code の CLAUDE.md、アプリの「Instructions for Claude」、プロジェクトの指示。どれも毎回読み込まれるので、同じ基準で見る。

- **長さ:** CLAUDE.md は1ファイル **200行未満** が目安。長いほど文脈を食い、守られにくくなる。`@` で取り込んだファイルも起動時に読み込まれるので、分けても軽くはならない [2][6]
- **書くもの** [1]:推測できないコマンド、標準と違う書き方の規約、テストのやり方、リポジトリの作法(ブランチ名など)、その案件固有の設計判断、環境のクセ、気づきにくい落とし穴
- **書かないもの** [1]:コードを読めば分かること、一般的な作法、詳しい API ドキュメント(リンクで足りる)、よく変わる情報、長い説明やチュートリアル、ファイルごとの説明、「きれいなコードを書く」のような当たり前のこと
- **構成:** 見出しと箇条書きでまとめる。段落のかたまりより守られやすい [2]
- **一部の場面だけで要るもの** は、skill か、パスを指定したルール(`.claude/rules/` に `paths` を付ける)に移す [2]
- **症状からの見分け方** [1]:
  - ルールがあるのに守られない → ファイルが長すぎて埋もれている
  - 書いてあることを質問してくる → 書き方があいまい
- **育て方:** コードと同じに扱う。うまくいかないときに見直し、定期的に削り、変えたら Claude の動きが本当に変わったかを見る [1]
- **公式の点検機能:** Claude Code では `/doctor prompt-audit` で、古いモデル向けの指示、存在しないファイルへの言及、ファイル同士の矛盾を探せる(v2.1.283 以降)。Claude Code の環境なら、この診断と併用をすすめる [2]

アプリの Instructions for Claude に入れるとよいもの [8][9]:自分の役割と仕事、使う略語や社内用語、出力の好み(形式・長さ・口調)。何度も繰り返している訂正は、ここに足す候補。

## 4. skill

- **説明(description)が呼び出しを決める。** 何をするかと、いつ使うかの両方を書く。具体的な言葉(扱うファイルの種類、定型文)を入れる。三人称で書く [3]。説明が似ている skill が複数あると、間違ったほうが選ばれたり、どちらも呼ばれなかったりする [6]
- **長さの上限:** 名前は64文字、小文字・数字・ハイフンのみで、`claude` `anthropic` は使えない。説明は API の仕様では1024文字まで [3]。アプリのヘルプには200文字までと書かれているので、呼び出しに効く言葉は前半に置く [5]
- **1つの skill に1つの仕事。** 大きな skill を1つ作るより、小さな skill をいくつか持つほうがうまく組み合わさる [5]
- **本文は500行未満。** 詳しい内容は別ファイルに分け、SKILL.md から直接リンクする(リンクの先からさらにリンクしない)。100行を超える参照ファイルには目次を付ける [3]
- **例を入れる。** 入力と出力の例があると、うまくいった状態が伝わる [3][5]
- **古くなる情報を本文に書かない。** 日付で変わる手順は、たたんだ「古いやり方」欄に移す [3]
- **テスト:** 少なくとも3つの場面で試す。使うモデル(Haiku・Sonnet・Opus)それぞれで試す。呼び出されるはずの言い方を何通りか試して、実際に読み込まれるか確かめる [3][5]
- **安全:** API キーやパスワードを書かない。人からもらった skill は、有効にする前に中身を読む [5]
- **副作用のある skill**(送信・公開・削除など)は、Claude Code では `disable-model-invocation: true` で、名前を呼んだときだけ動くようにする [1][6]

## 5. コネクタ・MCP

- 普段使っているツール(Slack、Gmail、Notion、CRM など)をつなぐと、コピペの手間が減り、最新のデータで仕事ができる [10]
- MCP はツールの名前だけが先に読み込まれ、使うときに詳細が読み込まれるので、つないでおくだけなら文脈はほとんど食わない [6]
- 「コネクタでつなぐ」と「skill でそのツールの使い方を教える」は組み合わせて使う。例:DB をつなぎ、skill にスキーマやよく使う問い合わせを書く [6]
- 使っていないものは外す。つなぎっぱなしで権限だけ広い状態を作らない
- 毎朝・毎週のように繰り返す作業は、定期タスク(スケジュール)にすると、席に着く前に終わらせておける。指示に「毎週月曜に」と書くだけでは動かない [10]

## 6. 決まった処理(hooks)と権限

対象は Claude Code です。

- 「`.env` を編集しない」のような指示は、CLAUDE.md や skill に書いても「お願い」にとどまる。必ず守らせたいなら hook で止める [6]
- 毎回のリンター実行や通知など、考えなくてよい処理は hook にする。文脈も食わない [6]
- 許可の確認が多すぎて流し読みになっているなら、信頼できる操作を許可リストに入れるか、サンドボックスを使う [1]

## 7. サブエージェントとモデルの役割分担

- **サブエージェントは「調べもの」を本筋から切り離すために使う。** 多くのファイルやページを読む作業を任せると、要約だけが戻り、本筋の文脈がきれいに保たれる [1][6]
- **モデルの指定:** Claude Code のサブエージェントには `model` を指定できる(`sonnet` / `opus` / `haiku` / `fable`、または `inherit`)。速くて安いモデル(Haiku)に回せる作業は回す。Cowork や Claude Code で Claude がサブエージェントを呼ぶときも、呼び出しごとにモデルを指定できることがある [11]
- **使いどころの線引き:** 並列にできる、文脈を分けたい、独立した作業ならサブエージェント。単純な作業、順番に進める作業、1ファイルの修正は直接やる [4]
- **確かめ役を分ける。** 作った本人ではなく、新しい文脈のサブエージェントに結果を検証させると、見落としを拾える。ただし「穴を探して」と頼むと何かしら挙げてくるので、正しさと要件に関わるものだけに絞らせる [1]
- 役割分担の例(チームで決めるときのたたき台):

| 役割 | 向くモデル | 仕事 |
|---|---|---|
| 司令塔 | 本筋のモデル(Opus など) | 計画、判断、最終のまとめ |
| 調査 | Haiku / Sonnet | ページやファイルを読んで要点を返す |
| 検証 | 本筋とは別の新しい文脈 | 結果の裏取り、反証を探す |

モデル名と、それぞれが得意なことは変わりやすい。具体的なモデル名を指示に書くなら、最新の状態を ai-updates-digest(「Claudeアプデ」)で確かめる。

## 8. 確かめる仕組み

- Claude は「できたように見える」ところで止まる。テスト、ビルド、スクリーンショットとの比較など、合否が出る確認方法を渡すと、自分で直しきれる [1]
- 「できました」だけでなく、実行したコマンドとその結果など、証拠を見せてもらう [1]
