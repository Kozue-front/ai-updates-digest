# Claude の設定の診断

今の設定を、公式のベストプラクティスに照らして診断し、直す。

このskillの価値は「それって本当にベスト?」に根拠で答えることにある。診断は必ず `references/best-practices.md` の基準に紐づけ、「なんとなく良さそう」で改善案を出さない。基準に無い好みの話は、改善案ではなく「提案(好み)」として分けて書く。

## 呼び方

| 定型文 | 診断する範囲 |
|---|---|
| `Claude診断` | 見えているものすべて |
| `Claude診断 skill` | skill だけ |
| `Claude診断 CLAUDE.md` | CLAUDE.md と `.claude/` の中だけ |
| `Claude診断 指示` | Instructions for Claude とプロジェクトの指示だけ |

定型文だけで呼ばれたら、確認の質問はせずにすぐ始める。

## 手順

### 1. 基準を読む

`references/best-practices.md` を読む。確認日から3か月以上たっていたら、出典を開いて変わった点が無いか確かめる(変わった点は手順4のレポートに書く)。

### 2. 棚卸し

いまの会話から **実際に見えるもの** だけを書き出す。見えないものを推測で埋めない。

| 対象 | 見る場所 |
|---|---|
| skill | 会話に出ている skill の一覧(名前と説明)。中身(SKILL.md)が読める環境なら読む |
| コネクタ・プラグイン | 使えるツールの一覧 |
| 定期タスク(スケジュール) | 定期タスクの一覧を見るツールがあれば、一覧を取る。無ければ「見えないので未診断」とする |
| Instructions for Claude | 会話に含まれていれば読む。無ければ、設定画面からコピーして貼ってもらうよう1回だけ頼み、貼られなければその項目は「見えないので未診断」とする |
| プロジェクトの指示 | プロジェクトの中の会話なら読む。無ければ同上 |
| CLAUDE.md・`.claude/`(Claude Code / Cowork のフォルダ) | ファイルが読める環境なら、`CLAUDE.md`、`CLAUDE.local.md`、`.claude/rules/`、`.claude/skills/`、`.claude/agents/`、`~/.claude/CLAUDE.md` を探して読む |

Anthropic 標準の skill やプラグインの skill は、持ち主が直すものなので、診断はするが改善案は「使い方」の提案にとどめる。

**どの版を見たかを控える。** プラグインの skill は、会話に入っている写しが古いことがある(同期が遅れる、古い会話を開いている など)。プラグインなら `plugin.json` の version を、リポジトリが分かるならその最新の版も控え、レポートの冒頭に「診断した版と日時」として書く。写しとリポジトリが食い違っていたら、新しいほうを確かめてから判定し、写しが古いこと自体は「見えなかったもの」に書く。

### 3. 診断する

基準の項目ごとに、棚卸ししたものを1つずつ照らす。判定は3つ。

| 判定 | 意味 |
|---|---|
| 🟢 良い | 基準どおり。直さなくてよい |
| 🟡 改善の余地 | 動くが、基準から外れている(長い、説明があいまい、置き場所が違う など) |
| 🔴 要対応 | 守られない・呼ばれない・矛盾している・安全上の問題がある(パスワードの直書き など) |

判定には必ず次を付ける:

- **根拠:** 該当する行や説明文の引用(短く)
- **基準:** `best-practices.md` のどの項目か(出典番号つき)

数を数えられるもの(行数、説明の文字数、skill の数、似た説明の skill の組)は、目で見積もらず、数えて書く。コード実行が使えるなら `wc -l` などで数える。

1つずつ見たあとに、**つながり** も点検する。個々の設定が基準どおりでも、組み合わせで動かないことがあるため。

- 指示や skill が前提にしているデータ・ツールに、コネクタがつながっているか(例:GA4 の数字を使う手順があるのに GA4 につながっていない → 毎回コピペになる)
- 「毎週月曜」「毎朝」のような定期の作業が、指示に書かれているだけになっていないか。指示に書いても Claude は自分から動き出さないので、定期タスク(スケジュール)の設定が要る
- 手順の順番に無理がないか(後の手順の結果を、前の手順で使っていないか)
- 同じ仕事を、指示・skill・プロジェクトの複数の場所で書いていないか
- 同じ用途のコネクタが2つ以上つながっていないか(例:同じサービスの公式コネクタと自作のコネクタ)。道具が重なると、Claude が毎回どちらかを選ぶことになり、結果がぶれる
- 定期タスクが、もう無い skill やつながっていないコネクタを前提にしていないか

推測で埋めない。たとえば「新しい CRM」がどれかは、会話に書かれていなければ〔 〕のまま残す。

**見えなかったものを判定の根拠にしない。** 定期タスクの中身や Instructions for Claude など、棚卸しで「見えない」としたものについて、「こう動いてしまう」と判定しない。気になる点は「見えなかったもの」に、確かめ方と一緒に書く。

**🔴 は確かめてから付ける。** 🔴 を付ける前に、ファイルの一覧を取る、実際に読み込む、スクリプトを動かすなどして、言っていることが今の状態で本当に起きるかを確かめる。確かめられなければ 🟡 にとどめ、「未確認」と書く。ファイルの移動・削除のコマンドを出すのも、確かめたあとにする。

### 4. レポートを出す

チャットに次の順で出す。表を使い、1件ずつの説明は2〜3文にする。

1. **まとめ:** 診断した版と日時、🟢🟡🔴 の件数、一番効く改善を1つ
2. **優先して直すもの(最大5件):** 🔴 を先に、次に効果の大きい 🟡。各件に「今」「直した後」「理由(基準)」を書く。直した後の文面は、そのまま貼れる形で出す
3. **置き場所の見直し:** 別の場所に移したほうがよいもの(例:プロジェクトの指示に書いてある長い手順 → skill に)
4. **良いところ:** 🟢 のうち、続けるとよいものを2〜3件(根拠つき。ほめ言葉だけにしない)
5. **提案(好み):** 基準には無いが、こうすると楽になるかもしれないもの
6. **見えなかったもの:** 診断できなかった対象と、診断するには何が要るか
7. **基準の更新:** 手順1で見つかった公式の変更(なければ省く)

### 5. 反映する(承認されたものだけ)

改善案は、ユーザーが「やって」「これとこれ反映して」と言ったものだけを反映する。黙って書き換えない。削除はしない(不要になったものは「削除してよいもの」として挙げるだけ)。

| 対象 | 反映のしかた |
|---|---|
| CLAUDE.md・`.claude/` のファイル | ファイルが書ける環境なら直接直す。直す前に差分を見せる |
| skill | skill を作る・直すツールがある環境(skill の提案カードなど)ならそれを使う。無ければ、直した SKILL.md を渡し、アップロードの手順を書く |
| Instructions for Claude・プロジェクトの指示 | 設定画面で貼り替えてもらう。貼る文面全体と、どの画面のどこに貼るかを書く |
| コネクタ | つなぐ・外すは、画面の場所を案内する |

組織で共有している skill やプロジェクトは、持ち主が決める。改善案に「持ち主に相談」と添える。

反映したあとは、変えたものごとに「どう試せば効いたか分かるか」を1行で書く(例:「このプロジェクトで◯◯と頼んで、△△の形で返ってくるか見る」)。

## 他のskillとの関係

- 最新の更新情報(新機能、提供終了など)は ai-updates-digest が集める。同じ会話に「Claudeアプデ」のレポートがあれば、その中の 🔁・➕・🛠️ を診断の材料にする
- 具体的なモデル名を改善案に書くときは、古い名前を書かないよう、ai-updates-digest で最新を確かめるか、「今の最新の Opus」のように役割で書く
